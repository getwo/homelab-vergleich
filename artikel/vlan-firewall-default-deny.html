Default-Deny zwischen VLANs richtig prüfen

Ein VLAN ist noch keine Firewall

VLANs trennen Broadcast-Domänen auf Layer 2. Sobald ein Router zwischen zwei VLANs routet, kann Verkehr zwischen ihnen fließen, sofern keine Regel ihn begrenzt. Gerade ein Netz für Kameras oder IoT braucht darum eine explizite Zugriffsentscheidung. RFC 1918 beschreibt private IPv4-Adressräume, aber private Adressen sind keine Zugriffskontrolle. „Beide Netze sind intern“ ist keine Sicherheitsregel. [1]

Lege für jedes Segment eine eindeutige Funktion fest: Verwaltung, Geräte, Gäste oder Server. Notiere anschließend benötigte Beziehungen, zum Beispiel Geräte zur lokalen Steuerzentrale oder Arbeitsrechner zu einer Administrationsoberfläche. Beschreibe Quellnetz, Zieladresse, Protokoll und Port, nicht nur den Dienstnamen. Ein allgemeines „IoT darf ins LAN“ macht die Segmentierung weitgehend wirkungslos.

Reihenfolge entscheidet über das Ergebnis

Ein praktikables Modell lautet: explizite Erlaubnis für nötige Verbindungen, erlaubter Rückverkehr für bereits aufgebaute Sitzungen, danach Sperre für neue Verbindungen zwischen den Segmenten. Zustandserkennung ist wichtig, damit Antworten auf erlaubte Anfragen nicht durch eine symmetrische Sperre verloren gehen. RFC 6092 erläutert dieses Prinzip für IPv6-CPE: Ausgehender Verkehr kann Zustandsinformationen erzeugen, nicht angeforderter eingehender Verkehr wird begrenzt. Das ist ein Prinzip, keine direkt auf jeden Hersteller übertragbare Routerkonfiguration. [2]

Halte Routerverwaltung, DNS und gegebenenfalls DHCP als eigene Fälle fest. DHCP-Relay oder lokale Resolver brauchen möglicherweise gezielte Ausnahmen. Stelle die Sperre niemals vor die einzige Administrationsverbindung, ohne einen getesteten Zugang vor Ort oder eine Rückfallmöglichkeit bereitzuhalten. Regeln für IPv4 und IPv6 getrennt prüfen, sofern das Gerät sie getrennt verwaltet.

Mit Gegenproben statt nur mit Logs testen

Prüfe zunächst eine erlaubte Verbindung mit einem tatsächlich erreichbaren Zielservice. Teste danach aus demselben Quellsegment ein verbotenes Ziel, auf dem ebenfalls ein Testdienst lauscht. Ein fehlender Ping allein beweist keine Firewallwirkung: Der Zielhost könnte ICMP selbst blockieren. Vergleiche Router-Log oder Regelzähler mit dem tatsächlichen Verbindungsversuch und protokolliere die erwartete Richtung. [2]

Teste zusätzlich den Rückweg einer zulässigen Sitzung und einen neu initiierten Verbindungsversuch in Gegenrichtung. So fällt eine versehentlich bidirektionale Erlaubnis auf. Nach Änderungen an Switch-Trunks kontrolliere, ob der Client wirklich im erwarteten VLAN gelandet ist. Pflege die Ausnahmeliste nach: Dienst abgeschaltet bedeutet Regel entfernen, nicht historische Öffnungen sammeln. Default-Deny ist eine kontinuierlich geprüfte Grenze, kein einmal gesetztes Häkchen.

Die VLAN-Grundlagen erklären die Layer-2-Trennung; pfSense und OPNsense betreffen die Router- und Firewall-Ebene.

Eine gute Regelmatrix enthält auch den Verbindungsinitiator. Die Steuerzentrale, die eine Kamera abfragt, benötigt womöglich einen anderen Weg als eine Kamera, die Ereignisse aktiv an die Zentrale meldet. Gleiche Zielports bedeuten nicht dieselbe notwendige Richtung. Für die Wartung kann ein zeitlich begrenzter Admin-Zugriff besser sein als eine permanente breite Freigabe. Kontrolliere außerdem, ob Multicast und Discovery-Protokolle über einen separaten Repeater weitergereicht werden; sonst sieht die TCP-Matrix sauber aus, während Geräteinformationen trotzdem segmentübergreifend auftauchen. Bei einem Testfehler zuerst die tatsächliche Client-IP, Netzmaske und Gateway-Zuordnung prüfen. Eine perfekte Firewallregel im falschen Interface bewirkt gar nichts.

Nach jeder Ausnahme die Gegenrichtung getrennt betrachten: Eine zustandsbehaftete Antwort ist etwas anderes als eine neue, vom weniger vertrauenswürdigen Netz ausgehende Verbindung. Die Regelprüfung sollte beide Fälle ausdrücklich unterscheiden.

Erstelle vor der Umstellung eine Regelmatrix mit je einem Eintrag für initiierende Seite, Zieladresse, Port, Adressfamilie und Verantwortliche. Prüfe bei DNS-Anfragen zusätzlich, ob der Resolver auf dem Router selbst oder in einem anderen VLAN liegt: Verkehr zum Router kann eine andere Regelkette treffen als Transitverkehr zwischen zwei VLANs. Eine erfolgreiche Namensauflösung beweist nicht, dass der eigentliche Zielservice freigegeben wurde.

Teste an einem Ziel mit nachweislich lauschendem Dienst: Aus dem erlaubten Verwaltungsnetz muss die Verbindung gelingen, aus dem Gästenetz muss ein neuer Verbindungsaufbau scheitern. Die Antwort auf die erlaubte Sitzung darf zurückkommen. Protokolliere beide Quell- und Ziel-IP-Adressen sowie die treffende Regel. Prüfe IPv6 getrennt, weil es einen anderen Pfad als private IPv4-Adressen nutzen kann.
