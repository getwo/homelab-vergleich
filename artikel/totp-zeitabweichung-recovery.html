TOTP: Wenn der richtige Code trotzdem scheitert

Die Uhr gehört zur Anmeldung

TOTP berechnet einen Einmalcode aus einem gemeinsamen Geheimnis und der aktuellen Zeit. RFC 6238 beschreibt den Zeitschritt als Eingabe und verwendet im Beispiel ein 30-Sekunden-Intervall. Schon eine abweichende Gerätezeit kann einen gültig aussehenden Code in das falsche Zeitfenster schieben. Der Dienst darf zur Toleranz benachbarte Schritte akzeptieren, erweitert damit aber zugleich die Zeit, in der ein Code verwendet werden kann. [1]

Wenn ein Code nicht funktioniert, kontrolliere zuerst Uhrzeit, Zeitzone und automatische Synchronisierung von Server und Authenticator. Zeitzonen allein ändern bei korrekt implementierter Unix-Zeit den TOTP-Wert nicht; eine falsch eingestellte Systemzeit dagegen schon. Mehrfaches hektisches Eingeben kann Rate-Limits auslösen. Teste mit einem neuen Code und dokumentiere die Abweichung, bevor du das Verfahren abschaltest.

Secret, Gerät und Recovery trennen

Der im QR-Code hinterlegte Seed ist ein dauerhaftes gemeinsames Geheimnis. Wer ihn kopiert, kann neue Codes erzeugen; ein Screenshot des Einrichtungsbildschirms ist deshalb eine sensible Kopie. RFC 4226 beschreibt das zugrundeliegende HOTP-Verfahren und die Bedeutung des gemeinsamen Geheimnisses, aus dem TOTP den zeitabhängigen Zähler ableitet. [2]

Lege Wiederherstellungscodes an einem vom Telefon getrennten Ort ab und prüfe, wie der Dienst einen verlorenen Authenticator ersetzt. Ein zweites Gerät kann vorbereitet werden, darf aber nicht still dieselbe unsicher exportierte Seed-Datei auf mehreren ungeschützten Geräten verteilen. Für besonders wichtige Adminzugänge ist eine weitere unabhängige Authentisierungsmethode zu erwägen. Eine Recovery-Mailbox sollte ihrerseits geschützt sein, sonst verlagert sich die Schwachstelle lediglich.

Fehlersuche und Wiederanlauf üben

Prüfe zuerst, ob nur ein Konto betroffen ist oder sämtliche TOTP-Anmeldungen desselben Geräts. Im zweiten Fall spricht vieles für eine falsche Uhr. Betrifft es nur einen Dienst, kontrolliere, ob der gespeicherte Seed noch zur aktuellen Einrichtung gehört und ob der Server zeitlich richtig läuft. RFC 6238 erläutert die Sicherheitsfolgen eines vergrößerten Prüfzeitfensters; die Lösung für einen schlecht synchronisierten Server ist nicht unbegrenzte Toleranz. [1]

Teste Recovery-Codes mit einem nicht kritischen Testkonto und halte fest, ob ein verwendeter Code danach ungültig wird. Prüfe auch den Weg nach einem Gerätewechsel: Muss TOTP neu eingerichtet, ein vorhandener Passkey genutzt oder ein Administrator zur Freigabe hinzugezogen werden? Bewahre einen getesteten administrativen Rückweg auf, ohne das zweite Merkmal dauerhaft abzuschalten. Eine funktionierende Uhr und dokumentierte Wiederherstellung machen aus TOTP einen brauchbaren Betriebsprozess statt eines improvisierten Notfalls.

Wenn mehrere Dienste denselben Identitätsanbieter verwenden, gehört dessen Ausfallweg in das SSO-Betriebskonzept. Ein Passwortmanager kann Recovery-Codes schützen; er darf jedoch nicht der einzige Zugangsweg zum gesperrten Konto sein.

Die Uhr des Authenticator-Geräts muss nicht denselben Zeitzonennamen wie der Server anzeigen; beide müssen denselben tatsächlichen Zeitpunkt kennen. Ein Vergleich der angezeigten Ortszeit ohne Zeitzonenbezug kann in die Irre führen. Nach einem Server-Restore oder einer VM-Migration ist die Systemzeit besonders prüfenswert. Speichere Recovery-Codes nicht ausschließlich im Konto, für dessen Anmeldung du sie brauchst. Kontrolliere bei der Einrichtung außerdem, ob das Abschalten von TOTP einen erneuten Login verlangt und alte Sessions ungültig werden. Bei Verlust des Geräts ist der Wiederzugang nur die erste Hälfte des Plans: Danach den alten Authenticator entfernen, neue Codes registrieren und vorhandene Sitzungen überprüfen. Sonst bleibt ein verlorenes Gerät möglicherweise weiterhin nutzbar.

Ein einmal akzeptierter TOTP-Code sollte laut RFC 6238 innerhalb desselben Zeitschritts nicht noch einmal erfolgreich einsetzbar sein. Prüfe dies mit einem harmlosen Testkonto, ohne echte Zugangscodes im Protokoll abzulegen. Unterstützt der Dienst Recovery-Codes, teste deren einmalige Verwendung separat und bewahre den verbleibenden Vorrat außerhalb des Authenticator-Geräts auf.
